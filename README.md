# 县域农村自建房安全巡查整改补助平台

围绕**一栋房屋档案**打通「巡查 → 乡镇复核（整改方案）→ 风险告知 → 停用/人员转移 → 施工计划与补助资格校验 → 施工材料/照片/进度 → **施工材料抽查（发票/进场照片/现场测量 → 偷换属实则限制接单、暂停补助、退回返工并重排节点）** → 逐项验收 → 县级销号 → 销号后复查」全链路，并把基层治理中的**协商成本**（户主、租户、经营者、老人家庭成员、村干部、施工队的态度与博弈）与 7 类异常事件沉淀在同一档案中。

技术栈：Vue 3 + Vite + Element Plus + Pinia / NestJS 10 + TypeORM / PostgreSQL 15，Docker Compose 一键启动。

---

## 一、快速启动（Docker Compose 一键）

```bash
docker compose up -d --build
```

- 前端：http://localhost:8080
- 后端 API：经前端容器 nginx 反代在 http://localhost:8080/api （后端容器 3000 端口未直接发布到宿主机）
- PostgreSQL：容器内 `db:5432`，库名/账号/密码均为 `postgres`，数据库 `rural_house`

首次启动后端会**自动建表并写入演示数据**（6 栋覆盖各治理阶段的房屋、6 类角色账号、2 支施工队）。重置数据：

```bash
docker compose down -v && docker compose up -d --build
```

## 二、本地开发启动（不用 Docker）

需本机 Node.js ≥ 20、PostgreSQL ≥ 13。

```bash
# 1. 建库
createdb -U postgres rural_house   # 或用 psql: CREATE DATABASE rural_house;

# 2. 后端（默认连接 localhost:5432, postgres/postgres）
cd backend
npm install
# 如数据库账号不同，用环境变量覆盖：
# export DB_HOST=localhost DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres DB_NAME=rural_house
npm run start:dev          # http://localhost:3000，首次启动自动建表+演示数据

# 3. 前端（新终端）
cd frontend
npm install
npm run dev                # http://localhost:5173 （已配置 /api 代理到 3000）
```

后端环境变量：`DB_HOST DB_PORT DB_USER DB_PASSWORD DB_NAME JWT_SECRET PORT`。

## 四、核心业务规则与"互相制约"设计

### 1. 风险规则引擎（巡查登记即自动定级）

输入房龄、层数、经营、出租、加层、墙体裂缝/屋面渗漏/地基沉降（无/明显/严重）、居住人数、雨季因素：

- **紧急转移**：地基沉降严重；或严重墙裂+加层；或雨季叠加严重结构隐患；或严重结构隐患+人员聚集；
- **暂停使用**：存在加层；结构隐患叠加经营/出租/多层/多人居住；墙裂+沉降双明显；雨季叠加结构隐患；
- **限期整改**：任一明显结构缺陷、严重渗漏、高房龄多层等；
- **一般关注**：仅老旧、轻微渗漏、经营出租登记等，纳入日常巡查。

### 2. 环节互相制约（后端强制，非前端提示）

| 环节 | 闸口规则 |
|---|---|
| 风险告知 | 方案要求停用/转移的，告知**必须签收**，否则不能封停、不能转移、不能开工 |
| 停用/转移 | 未告知签收不得封停；要求紧急转移的未落实安置不得开工；转移人员**验收销号前不允许返回** |
| 阻断异常 | 农户拒改、租户不搬、偷换材料、补助争议、验收不通过、问题反弹等未办结时，**冻结开工/验收/销号**；办结必须填写处置结果 |
| 施工开工 | 须同时满足：已告知（且按要求签收）→ 已停用/已转移 → 户主签署整改同意书 → 施工队资质有效 → 预算明细完整；任一不满足直接 400 |
| 材料核验 | 施工日志填写的进场材料名称+规格与预算明细自动比对，不一致即判定**偷换材料**，自动生成阻断异常 |
| 施工材料抽查 | 验收人员可对加固完成照片发起抽查：施工队必须上传**材料发票、进场照片、现场测量结果**三类材料；判定**偷换属实**自动联动：① 施工队列入**限制接单名单**（解除前不得承接新工程）；② 农户补助**拨付暂停**（状态置为 SUSPENDED，发钱被后端拒绝）；③ 整改任务回到**返工状态**、必改项退回待施工；④ 重新记录**验收节点与补助拨付计划**。返工整改提交后须**对照原方案逐项复验**，合格才解除限制、恢复拨付并重新安排逐项验收 |
| 补助申请 | 8 项资格校验（困难类型、困难证明、权属证明、户主同意、方案告知、高风险停用/转移、预算、施工队资质）全过才进入乡镇复核；金额 ≤ min(预算70%, 5万) |
| 补助审批 | 存在未办结**补助资格争议**时禁止批准 |
| 补助发放 | 即使已批准，**未销号不得发放**（防"带病拨款"）；材料抽查暂停拨付期间同样拒绝；已发放不可重复发 |
| 验收 | 必改项逐条给出结论、**填写逐项核验意见、合格项逐项上传现场核验照片**，并须勾选"已对照原方案逐项确认"——**不能只凭一张完工照片关闭任务**；且施工状态必须"已完成"、返工期间（REWORK）冻结验收入口；任一条不合格→整体不通过→退回整改并开阻断异常 |
| 销号 | 仅"验收通过待销号"可销号；县级须勾选"逐项完成"与"安全恢复/非数字销号"双确认；销号后准许转移人员返回 |
| 复查反弹 | 销号后复查 FAIL → 状态置为"问题反弹"、回写新隐患、开阻断异常；须重新复核→施工→验收→销号，支持多轮治理 |

### 3. 协商成本建模

- **利益相关方台账**：户主/租户/经营者/老人家庭成员/村干部，记录态度（支持/观望/抵触）与对进度的影响；
- **协商记录**：议题、参与方、协商结果，进入档案时间线；
- **7 类异常事件**：农户拒绝整改、偷换材料、补助资格争议、雨季风险加重、租户不愿搬离、验收不通过、复查反弹；区分是否阻断流程。

### 4. 县级看到的不是"数量销号"

驾驶舱直接暴露治理真实性指标：高风险房屋总数与**真正停用/处置率**、高风险未停用督办清单（点进即可处置）、销号率与**反弹数**、整改项逐条完成率（含不合格数）、补助各环节数量与累计发放额、分乡镇对比。

## 五、验证方式与已执行的验证结论

### 已实际执行

1. **后端类型检查与生产构建**：`tsc -p tsconfig.build.json` 通过，`dist/main.js` 可由 `node` 直接启动。
2. **前端生产构建**：`vite build` 通过（1689 模块，产物 0 错误），`vite preview` 验证 `index.html` 与 JS 资源均 HTTP 200。
3. **全新 PostgreSQL 15 实例集成验证**：用编译产物对空库启动，自动建表+种子数据写入成功，登录签发 JWT 正常。
4. **端到端业务制约脚本（53 项断言全部 PASS）**，覆盖：
   - 偷换材料自动生成阻断异常，未办结时验收/提交计划均被 400 拒绝；办结必须填写处置结果；
   - **施工材料抽查全流程**：发起抽查 → 举证三类材料（发票/进场照片/现场测量结果，缺项被拒）→ 判定"偷换属实/不存在偷换"；属实时限制接单名单、补助 SUSPENDED 且发放被拒、限制施工队承接新工程被拒、房屋回返工状态、验收被冻结；未整改不能复验、复验结论必填；返工复验合格后自动解除限制、补助恢复 APPROVED、阻断异常办结、返工后逐项验收通过；
   - 验收**必须勾选对照原方案逐项确认**、逐项意见与合格项现场照片缺一被拒；
   - 暂停使用房屋告知未签收被拒；阻断异常+未告知时开工被拒；
   - 已销号房屋补助已发放、转移人员 `allowReturn=true`、补助不可重复发放、未销号禁止发放；
   - 验收不通过自动开阻断异常，未办结不能重新验收；
   - 复查反弹 → 重新复核 → 重新验收 → 二次销号全链路；
   - 角色越权（农户登记巡查/判定抽查 403、施工队发起抽查 403、乡镇销号 403、未登录 401）；
   - 县级驾驶舱统计（风险/状态/乡镇分布、高风险停用率、补助汇总含暂停拨付、**限制接单施工队名单**、7 类异常、整改项完成率）数值与种子数据一致。
